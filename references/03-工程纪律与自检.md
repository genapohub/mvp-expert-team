# 03 · 工程纪律与自检（AI 生成代码的防事故底座）

> 来源：专家包 01-standards 11 篇中的核心方法论（其中 10 篇改编自 UmaDev 知识库，MIT License）。本文件为工程纪律的可执行浓缩——解决"AI 写的代码能不能信"的问题。
> 一句话立场：**AI 代码的默认假设是"能跑就行但细节不可信"，所有纪律都围绕把不可信变成可验证。**

---

## 一、五层工程化体系（商业交付 DNA）

| 层 | 名称 | 落地 |
|----|------|------|
| 1 | 标准化需求工程 | Phase 0 澄清 + Phase 1 PRD |
| 2 | 项目级上下文系统 | Spec + 项目状态文件 |
| 3 | 角色级编排 | 并行调研/开发（子代理或角色切换） |
| 4 | 企业级规范约束 | 每阶段质量门禁 + P0 规则 |
| 5 | 实时可观测性 | 进度汇报 + 决策日志 + 交付证据 |

**数据支撑**：同模型 + 同需求，无流程门禁完成率约 60%，有 Harness 门禁达 98%。流程即质量，不是控制狂。

## 二、代码组织规范（code-organization · 硬门禁）

### 分层依赖（只能向下）
Routes/Controllers（参数校验→调 service→组装响应）→ Services（业务逻辑/事务编排）→ Repositories（数据访问）→ 基础设施（DB/Redis/三方）。

### 文件组织硬规则（出现即不合格，退回重做）
| 规则 | 要求 |
|------|------|
| 单一职责 | 一个文件一个主职责、一个主导出 |
| 单文件 ≤300 行 | 超限必须按子功能拆（不含空行注释） |
| 按资源分包 | 一资源 = controller + service + repository 三件套 |
| 入口只装配 | app.ts/main.py 只挂中间件+路由+启动，零业务 |
| 逻辑下沉 | 业务逻辑进 service，不进路由处理器、不进 utils |
| 类型/Schema 独立 | 请求校验、类型定义单独成文件 |

门禁命令：`find src -name '*.ts' | xargs wc -l | awk '$1>300{print "OVER:",$0}'`

## 三、生成式代码失效模式（6 类 · 每次交付前逐项核对）

| # | 失效模式 | 危害 | 自查方法 |
|---|----------|------|----------|
| 1 | Happy-path 偏差 | 只写了成功路径 | 错误/边界/超时分支是否齐全？ |
| 2 | **沉默逻辑错误**（最致命） | 未测行为悄悄算错：货币计算/时区/权限取反/事务隔离/分页 off-by-one | 逐项核对会"悄悄算错"的点 |
| 3 | 幻觉依赖/接口 | 编造不存在的包或 API 签名 | 新增依赖是否真实？API 是否对照文档？版本是否锚定？ |
| 4 | 缺失系统上下文 | 忽略权限/限额/多租户隔离/网络策略 | 逐项验收系统级约束 |
| 5 | 性能盲区 | N+1 查询/循环内 IO/无分页/无索引/无超时 | 扫热点路径 |
| 6 | 静默缺失 | 漏 import/未处理 Promise/未 close 连接 | lint + 审查兜底 |

## 四、测试纪律（test-discipline）

### 测试金字塔（自底向上）
大量 Unit（函数/工具）→ 中等 Integration（API+DB）→ 少量 E2E（核心用户旅程）。

### 先写测试（顺序变革）
Spec 锁定 → QA 先写测试用例（基于 EARS 验收标准，覆盖正常/异常/边界/权限/状态）→ 开发按测试实现 → QA 跑测评审。
**原理**：写实现又写测试产生"同义测试"——测试复述实现假设，绿灯零信息量（实验数据：分角色 91.5% vs 同 agent 86.8% pass@1）。

### 反作弊门（见 ref 03 QA 卡 §反作弊）——AI 测试的 5 种作弊全部 P0 阻断。

### 回归集纪律
P0 缺陷修复 → 沉淀回归用例 `tests/regression/` → 进版本库每次改动都跑 → 只增不轻易删。
质量报告指标：回归率（旧行为由绿转红）= 0 才算完成；返工 ≤3 轮。

## 五、验证者/评审者模式（verifier-critic）

### RoleVerdict 结构化裁决
所有"评审另一角色产出"的场景，输出必须结构化：
```
verdict: pass | fail
blocking: [{违反项, 证据, 期望}]   // fail 必填
advisory: [{建议项, 理由}]
evidence: [{artifact_ref, line, 说明}]
```

### 诊断式打回
fail 必须指明"未满足哪条验收标准 + 证据 + 期望"，禁止"去改改"这类无信息指令。

### 过度设计护栏（评审者只标三类阻断）
1. 正确性缺陷
2. 需求未满足
3. 契约/安全/数据完整性破坏
**不标**：风格偏好、未被要求的额外特性、为覆盖率而覆盖率。

### Bounded（次数上限）
打回-重做最多 3 轮；连续 3 轮无进展 → 升级通知用户或停下，不无限循环。

## 六、上下文工程与自学习记忆

### 上下文工程要点
- 长任务防坍缩：关键契约（Spec/验收标准/Token）常驻工作上下文最前。
- 角色 spawn/切换时注入：角色定义 + 任务 + P0 红线 + 相关知识库路径 + 已知坑（按技术栈指纹召回）。
- 增量增删纪律：经验文件禁止整篇重写；只追加/修正与本次相关的具体条目。
- 一条好的经验："在 X 情形下因为 Y 会踩 Z，应当 W" ≫ "要注意质量"（被反复总结磨平的空话无价值）。

### 踩坑自学习四阶段闭环
1. **识别**：报错归类（dependency/type/runtime/cors/build/test），生成稳定签名（剥离路径/行号/版本号）。
2. **记录**：`pitfalls.jsonl` 落条；同签名只加 episode，不重复；300 条上限最久未命中淘汰。
3. **触发**：下阶段按**技术栈指纹交集**召回（如依赖 react-router-dom 则召回相关坑），注入"已知坑提醒"。不靠需求文字匹配。
4. **验证**：真实 build/test/lint 通过才标 `validated: true`；复发标 `recurring: true` 换策略。**只认机械证据，不认"我觉得修好了"。**

### 悬而未决登记册
定不下来 → 立即记 `docs/decisions/OPEN-DECISIONS.md`（含 Blocked By/Resolves When）。三类固定 slug：等外部条件 / 设计待评估 / 既有边界。只追加 + 就地关闭；每 Phase 开始复现未决项尝试关闭；关闭可升格 ADR。

## 七、生产就绪记分卡（7 × 3 矩阵）

> 评级 = QA/运维在交付前的最终关卡。总档取各维**最低档**（木桶原理），未达 **Silver 不交付商业生产**。

| 维度 | Bronze | Silver | Gold |
|------|--------|--------|------|
| 测试 + 回归 | 有冒烟 | 冒烟+功能+回归，反作弊通过 | +E2E 核心流 + 覆盖率 ≥80% |
| 契约 | 手工对齐 | openapi.yaml 自动生成类型 | 契约测试双端自动校验 |
| 安全 | 有 HTTPS | OWASP MVP 查项通过 | +安全扫描进 CI |
| 无障碍 | 键盘可达 | WCAG 2.1 AA 主要合规 | +自动化 a11y 测试 |
| 性能 | 可加载 | p95 <500ms / 首屏 <3s | +Lighthouse >70 + 压测 |
| 可观测 | 有日志 | /health + 错误监控 + 告警 | +指标仪表盘 + 告警闭环 |
| 发布安全 | 可手动回滚 | 一键回滚 + 备份生效 | +灰度发布 + 迁移演练 |

## 八、质量门禁汇总（全流程一表）

| Phase | 门禁 | 执行者 | 不通过后果 |
|-------|------|--------|------------|
| 0 | 需求 3 句话确认 | 主控 | 不进调研 |
| 1 | 用户确认三文档（唯一必扰交互点） | 用户 | 不进 Spec |
| 1 | P0 红线嵌入每个角色指令 | 主控 | 下发时必含 |
| 1.5 | Spec 12 章完整 + 图标库锁定 | 主控 | 内部流程 |
| 2 | emoji 正则扫描设计输出 | 主控 | 退回设计 |
| 2 | 反模式检查（7 大罪 + P0） | 主控 | 退回设计 |
| 2 | 机器产物 openapi.yaml / design-tokens.json 存在 | 主控 | 不放行 Phase 3 |
| 3 | emoji 扫描前端代码 | 主控+前端 | 立即替换 |
| 3 | 自检循环 lint/type/test | 前后端 | 自动修 ≤3 轮 |
| 3 | 代码组织（分层/≤300 行/单一职责） | 主控+前后端 | 退回重做 |
| 3 | UI 视觉检查（19 项 + P0） | 前端+主控 | 退回前端 |
| 4 | P0 规则全量扫描 | 主控+QA | 打回开发 |
| 4 | P0 缺陷归零 + 反作弊门 | QA | 不能进部署 |
| 4 | 生产就绪 ≥ Silver | QA+运维 | 不交付商业生产 |
| 4 | 部署验证（health + 核心流 + 回滚） | 运维 | 不能交付 |
